## ボトルネック上位

### 1. 友達フィードのクエリ (DB)
- 根拠: `WITH me AS (...)` が 18,001回、平均 1.24ms、合計 22.3秒、DB 時間の 16.6% (#32078: 18,390回 / 1.14ms / 18.2%)
- 原因箇所: `go/post.go` (閲覧者のコンテキスト取得)
- 対策案: `EXPLAIN (ANALYZE, BUFFERS)` で、友達の友達の `UNION ALL` と `json_agg` の比率を確認する。リクエスト内の重複取得を避ける
- 期待効果: 中。1.8万回呼ばれる

### 2. ユーザー検索 (DB)
- 根拠: `SELECT id, username, ... FROM users WHERE status=$5 AND id<>$1 AND (...)` が 4,188回、平均 **4.04ms**、合計 16.9秒、DB 時間の 12.6% (#32078: 3,674回 / 2.76ms / 8.8%)。その前の #30207 では 10.88ms だったので、ベンチごとの差が大きい
- 原因箇所: `go/user_read_api.go`
- 対策案: 実際の検索語で `EXPLAIN (ANALYZE, BUFFERS)` を取り、短い検索語と長い検索語で、ソート・ブロック判定・ページングのどこが時間を使うかを確認する
- 期待効果: 中。検索は 1件 2点で、asia1 の API の平均が +12% に伸びている

### 3. 画像本体のファイルが無いときの DB 読み込み
- 根拠: `SELECT data, created_at <= (SELECT created_at FROM initial_data_boundary) AS initial ...` が 964回、平均 5.41ms、合計 5.2秒、DB 時間の 3.9% (#32078: 1,125回 / 5.63ms)
- 原因箇所: `go/image_store.go` (`load`。ファイルが無い初期データの画像・プロフィール画像を DB から読む)
- 対策案: どの画像がファイルに無いかを調べ、初期データの画像を asia1 にすべて書き出す (`go/image_extract.go`)
- 期待効果: 小

### 4. 画像の閲覧権限クエリ (DB) — #48 は維持
- 根拠: 16,748回、平均 0.45ms、合計 7.5秒、DB 時間の 5.5% (#32078: 15,524回 / 0.48ms)。#13634 の 1.55ms、#28870 の 2.97ms から下がったまま
- 期待効果: 小 (対応済み)

### 5. asia1 の「その他」の枠の待ち
- 根拠: asia1 の `GET /api/me` 3.380s、`PATCH /api/me` 2.135s、`GET /api/users` 1.542s、`POST /api/friend-requests` 1.442s、`GET /api/images/:id` 1.162s。heavy の枠を増やして、その他の枠を 12 → 8 に減らしたため、少し長くなった
- 原因箇所: `go/priority.go` (`splitPriorityLimits`)
- 対策案: 枠の配分は、全体の処理量が変わらない以上、ゼロサム。asia1 の CPU は idle 65% あるので、枠の合計 (`ISUREAL_PRIORITY_LIMIT` = 32) 自体を増やせるかを、CPU と DB の余裕を見ながら試す
- 期待効果: 中 (推測)
- リスク: 枠を増やすと、DB の接続・CPU を使い切る可能性がある (asia2 の idle 5% 未満が 10秒ある)

## PR #74 の判定

- 狙いの指標 (memories と export) は改善し、その他の API は +2〜+56% 遅くなった。asia1 の CPU の使い方は変わらない
- スコアの -4.0% は、europe の最後の期間の投稿が減ったこと (PR #74 の対象外) などの人数のぶれで説明できる範囲で、**PR #74 が原因とも、効果が無いとも言えない**
- **マージの判断:** 悪化の根拠は無く、heavy の API の改善は実測で確認できた。一方、スコアでの効果は、1回のベンチでは測れない。2回目のベンチ (同じ構成) で、スコアのぶれの大きさを測ってから決めるのが安全
