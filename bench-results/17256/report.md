## ボトルネック上位

### 1. asia の最後の期間の取りこぼし (asia1 の飽和)
- 根拠: asia の最後の期間は 319件中107件 (34%)、グランプリ アジア 69人 / 483人。投稿→フィード p50 4.35s (他の期間は 1.22s)。asia1 は t≈40〜90 で idle 0〜6%、iowait 最大29%。pprof flat 1位は `Syscall6` 26.5%
- 原因箇所: `go/image_store.go` の `readImageFile` / `writeFileAtomic` (ファイルの読み書きと fsync)、`createPostHandler` (cum 8.96s)、`exportPostsHandler` (cum 5.50s、うち `ImageStore.load` 4.28s)
- 対策案: #16464 の報告と同じ (投稿の画像の fsync をまとめる、初期画像の読み込みを europe1 / america1 に分散する)
- 期待効果: 大。グランプリの asia は1件20点で、残りが約410人
- リスク: 再起動後のデータ保持

### 2. 負荷の山での DB (asia2)
- 根拠: t≈40〜50 に asia2 の idle 5% (us 80%)。slow.txt 1位はユーザー検索 2143回 / 平均 15.10ms / DB 時間の 21.0%、2位は画像の閲覧権限 12659回 / 1.98ms / 16.3%、3位は友達フィードの `WITH me AS` 12147回 / 1.49ms / 11.7%
- 対策案: ユーザー検索のインデックスまたは結果のキャッシュ (#15916 の報告と同じ)
- 期待効果: 中。人数が増えた分、DB の山が前より高い

### 3. 後半の admin の待ち
- 根拠: t=46 以降の admin は 0.20〜0.80s (それより前は0.07s以下)。asia の最後の期間の admin が 0.80s で最も遅い
- 原因箇所: `go/admin_posting_window_api.go` の `lockPostingWindowRegionExclusive` と `UPDATE posting_windows SET ended_at`。投稿の `FOR SHARE` (`go/post_api.go:114`) と、登録などの共有ロック (`go/user_api.go:94` など) を待つ (推測)
- 対策案: 登録・リージョン変更・退会の共有ロックをやめる (通知の行を作らなくなったので不要)。投稿の `FOR SHARE` を外せるか調べる
- 期待効果: 小〜中。期間の開始がずれると、SSE のつなぎ直しが間に合わないユーザーが出る (#11801)
