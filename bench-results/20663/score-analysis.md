# ベンチ #20663 スコアを上げるための分析

score 105922。配点は docs/manual.md「スコアの計算」。数値は access.log (timeline.tsv) とポータルの Stdout から出した。

## 結論

1. **europe / america の人数が5日目に増えなかった。ここが最大のレバー (推定 +2〜3万点)**
   - 人数の推移: europe 7→17→48→114→**114**、america 6→15→41→96→**96** (asia は 873 まで増えた)
   - europe / america の4日目は、asia の4〜5日目と同じ時間帯 (t≈45〜60) にある。このとき asia1 が張り付き、asia1 へ転送される europe / america の API が遅くなった。その結果、その日に来た新規ユーザーが期間内に投稿まで進めなかった
2. **asia の最後の期間 (1件20点) で、約240人が締め切り (t≈77) に1秒以内で間に合っていない (+約5千点)**
3. どちらも、負荷の山 (t≈45〜78) の asia1 と asia2 の処理を軽くすれば効く。平均の CPU (asia1 idle 60%) を見ても意味が無い

## スコアの内訳 (推定)

| 項目 | 点 | 根拠 |
|---|---|---|
| 投稿後の友達フィードの検証 (通常の期間、10点) | 約20,600 | 期間内の完了: asia 1404、europe 257、america 181 (×1.5) |
| 同 (最後の期間、20点) | 約17,200 | t=77 までの完了: asia 550、europe 111、america 95 (×1.5) |
| それ以外 (閲覧・画像・Memories・友達申請・エクスポートなど) | 約68,000 | 残り |

- 友達フィードの検証は全体の約36%
- それ以外の約68,000点を、のべ人数 (リージョンの倍率をかける) の約3,500人日で割ると、1人1日あたり約20点になる
- 人数が増えれば、検証と閲覧の両方が比例して増える

## 1. 人数が増えるかどうかは、前の日の完了率で決まっていそう (推定)

期間の順番は asia → europe → america (admin の作成時刻と Stdout の「N 日目」の時刻が一致する)。この順番で、日ごとの「その日の人数」に対する「期間内に投稿〜友達フィードまで完了した人数」を出した。

| | 1日目 | 2日目 | 3日目 | 4日目 | 5日目 |
|---|---|---|---|---|---|
| asia 完了/人数 | 16/18 (89%) | 47/49 (96%) | 138/142 (97%) | 390/406 (96%) | 813/873 (93%) |
| 翌日の倍率 | ×2.7 | ×2.9 | ×2.9 | ×2.2 | — |
| europe 完了/人数 | 7/7 | 17/17 | 46/48 (96%) | **87/114 (76%)** | 100/114 |
| 翌日の倍率 | ×2.4 | ×2.8 | ×2.4 | **×1.0** | — |
| america 完了/人数 | 6/6 | 15/15 | 40/41 (98%) | **47/96 (49%)** | 73/96 |
| 翌日の倍率 | ×2.5 | ×2.7 | ×2.3 | **×1.0** | — |

- 完了率が 89% 以上の日は必ず翌日に増え、76% 以下の日は増えていない。閾値は 76〜89% の間にありそう
- ただし docs/user-growth-analysis.md には、#8691 で asia の完了率が100%でも増えなかった例がある。当時は他の条件 (admin の遅さなど) が効いていた可能性がある。**閾値は推定で、1回のベンチからしか出していない**
- #20097 (europe 98→99、america 62→62) と #18039 も5日目に止まっている。止まっていない #17256 (europe 121→198、america 82→135) は、asia の人数が少なかった (4日目 397、5日目 481)

### europe / america の4日目で何が起きたか

- 期間: europe t=47.2〜57.1、america t=50.3〜60.1。asia の4日目 (t=44.1〜53.5、406人) と5日目 (t=53.5〜、873人) に重なる
- その時間の asia1: us 37.6 / sy 34.9 / idle 6.4 / wa 15.7。asia2 (DB): idle 10.9
- europe1 の応答時間 p50 は、t=40〜50 で 0.17s、t=50〜60 で 0.49s、t=60〜70 で 0.74s。america1 もほぼ同じ (ほとんどが asia1 への転送)
- 投稿しなかったのは、主にその日の新規ユーザー
  - europe: 新規 66 のうち 15 が投稿せず、既存 63 のうち 17 が投稿せず
  - america: 新規 54 のうち 22 が投稿せず、既存 54 のうち 19 が投稿せず
  - 集計は接続元の host ごとで、ユーザーごとではない。目安として見る
- 新規ユーザーは期間中に register → login → PUT /api/me/profile-image → GET /api/me → 画像 → PATCH /api/me や友達申請 → … → 投稿 と進む
  - 新規ユーザーが投稿するまでの時間 (p50) は europe 6.0s、america 7.7s。期間は約9.8秒
  - 1リクエストが 0.5〜0.7秒かかると、期間内に投稿とフィードまで終わらない

### 増えた場合の見込み (推定)

- europe / america が5日目に ×2.4 になれば、europe +160人、america +134人
- 5日目と最後の期間で、1人あたり (20 + 10) + (20 + 20) = 約70点。×1.5 × 294人 ≈ **+3万点**
- 人数が増えると asia1 への転送も増える。全員が完了できるとは限らないので、+2〜3万点と見る

## 2. asia の最後の期間で、締め切り直後に完了している

- Stdout のグランプリ: asia 555 / 872人。ログでは、最後の期間に asia の 828人が投稿し、790人が友達フィードまで終えている。そのうち t=77 までに終えたのは 550人
- t=76 で 369人、t=77 で 550人、t=78 で 790人。約240人が締め切りに1秒以内で遅れている
- 最後の期間の投稿→フィードは p50 4.88s / p90 6.30s。通常の期間 (1.13s) の4倍。3リージョンの約1000人が同時に投稿するため
- 1秒速くなれば最大 +240人 × 20点 ≈ **+4,800点**

## 打ち手 (スコアへの効果が大きい順)

### A. 負荷の山で、europe / america から転送された API を優先する
- asia1 で、転送元が europe / america のリクエスト (ingressRegionHeader で判定できる) を asia のリクエストより先に処理する。例: asia のリクエストの同時実行数をセマフォで絞り、europe / america は絞らない
- 狙い: europe / america の4日目の完了率を 89% 以上にし、5日目に人数を増やす (推定 +2〜3万点)
- リスク: asia が遅くなる。asia の最後の期間 (打ち手 B) と相反する。asia の5日目の人数は最終日まで変わらないので、asia の4〜5日目を少し遅らせても失うのは主に asia の5日目と最後の期間の完了。投稿期間ごとに見て調整する
- ベンチマーカーを識別するのではなく、リージョンで扱いを変えるだけ。レギュレーションの「ベンチマーカーだけを識別して別の結果を返す」には当たらないと考える (未確認)

### B. 負荷の山の asia1 / asia2 を軽くする (A・B 両方に効く)
効果が見込める順。数値は asia1 の pprof と asia2 の slow.txt から。
1. ユーザー検索の SQL (DB 時間の26%、平均 19.7ms)。新規ユーザーのオンボーディング (友達を探す) に入っている。`go/user_read_api.go:80`
2. 投稿のレスポンスでの画像の署名 (asia1 の CPU 約6%)。空いている europe1 / america1 に計算させる。`go/image_signature.go:116`
3. プロフィール画像のアップロード (readUpload 3.86s + jpeg.Decode 1.26s)。新規ユーザーが最初に必ず叩く。europe / america 経由のものは、転送元のサーバで JPEG の検証をしてから転送すれば、asia1 の CPU が空く
4. エクスポートの画像のディスク読み (3.86s)

### C. 期間の作成 (admin) を速くする
- 5日目以降の admin は 0.5〜1.0s かかっている (t=53〜60)。期間の開始が遅れる分、期間内に動ける時間が減る
- 4日目の europe / america の admin は 0.14s / 0.24s で、大きな要因ではない
