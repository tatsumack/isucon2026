- ブランチ: `perf/image-url-expiration-step` (`37ede3f`) = main (`04dd5ca`、#50 署名の計算を europe1 / america1 へ移す、を含む) + #49 (`imageURLExpirationStep` を1分 → 1時間)。4台にデプロイ

- 結果: **PASS / score 81400**。#15916 (#50 のみ、77148) から **+5.5%**。ベンチ1回ずつの比較なので、ぶれを含む

## 計測で欠けているもの・混ざっているもの

- asia1 で計測開始の約86秒後から `du` が動いていた (チームの誰かの調査と思われる)。t≈86〜120秒の asia1 のディスク読み込み (最大 125MB/s) と iowait (約47%) は、ほぼこの `du` による。asia1 の平均は t=20〜85秒 (負荷走行中) で計算した
- timeline/report.txt は作っていない

## 概況

- **#49 の効果は小さい**
  - 署名の計算 (`computeImageSignature`) の CPU 時間: europe1 6.38s → 6.02s、america1 6.04s → 5.48s。合計 12.4s → 11.5s (**-7%**)
  - asia1 に残った `sha256.blockAVX2` は flat 2.55s (5.9%)。#15916 は 2.74s (6.0%) でほぼ同じ。内訳は `issueImageSignature` 2.69s (新しい投稿の応答)、`imageSignature` 0.56s (画像取得時の検証)
  - Memories と export は毎回違う画像を返すことが多く、1時間の間に同じ署名を使い回す機会が少ないと考えられる (推測。キャッシュの当たり率は測っていない)
  - スコアの +5.5% が #49 によるものかは判断できない
- **ボトルネックの所在: asia1 のディスク I/O と CPU (sy)**
  - asia1 の負荷走行中 (t=20〜85秒): us 29.4 / **sy 29.4** / idle 20.2 / **wa 21.2**、読み込み 42MB/s、書き込み 38MB/s (#15916 は wa 16.6、読み 40MB/s、書き 44MB/s)
  - 計測開始から約50〜85秒は idle 0〜6%。`kswapd0` も動いている (asia1 の空きメモリは 375MB、page cache 1.7GB)
  - 画像ファイルは asia1 に **17GB** (`/home/isucon/images`)。メモリ 3.8GB に収まらないので、初期画像の読み込みは毎回ディスクに行く (推測。キャッシュの当たり率は測っていない)
  - pprof flat の 1位は `Syscall6` 26.9% (#15916 は 25.6%)、2位は `memclrNoHeapPointers` 9.3%
- **asia1 の投稿が遅くなった**
  - asia1 `POST /api/posts`: 846回 平均 0.536s → **1074回 平均 1.025s**。europe1 0.887s → 1.119s
  - 投稿は件数が +27% 増えた。投稿1件ごとに画像ファイルを fsync する (`go/image_store.go:214` `writeFileAtomic`、ファイルとディレクトリの2回)。ディスクが混んでいる時間帯に投稿が待たされていると考えられる (推測)
- europe1 / america1: idle 94%。asia2 (DB): idle 70.5%、iowait 4.8%

## ボトルネック上位

### 1. asia1 のディスク I/O (画像ファイルの読み書き)
- 根拠: 負荷走行中の iowait 21.2%、読み 42MB/s・書き 38MB/s。`Syscall6` が pprof flat の 26.9%。asia1 の `POST /api/posts` が平均 1.025s
- 原因箇所: `go/image_store.go:214` (`writeFileAtomic` の fsync)、`:204` (`readImageFile`)
- 対策案
  - 投稿の画像の fsync をやめる、またはまとめる。ただし「ベンチ実行時に書き込まれたデータは再起動後にも取得できること」(レギュレーション) を守る方法が必要 (例: DB にも書いておき、起動時にファイルを復元する)
  - 初期画像の読み込みを europe1 / america1 にも分散する (各サーバに初期画像を持たせる)
- 期待効果: 大
- リスク: 再起動後のデータ保持 (追試で失格になる)

### 2. ユーザー検索のクエリ (DB)
- 根拠: 2083回、平均 16.10ms、DB 時間の 19.0% (#15916 は 14.81ms、18.6%)。asia1 `GET /api/users` 平均 0.440s
- 対策案: #15916 のレポートと同じ (インデックス、結果のキャッシュ)
- 期待効果: 中

### 3. 画像の閲覧権限の確認クエリ (DB)
- 根拠: 11537回、平均 2.40ms、DB 時間の 15.7%
- 期待効果: 中

### 4. export の一覧クエリ (DB)
- 根拠: 245回、平均 67.74ms、DB 時間の 9.4%
