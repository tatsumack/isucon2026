## ボトルネック上位
### 1. asia1 のディスク待ちで、asia の4日目が期間内に終わらない
- 根拠: asia1 の vmstat で、t≈52〜60 に id 0、wa 49〜71%、bi 14〜52MB/s。他の API の p99 が 1.0〜1.2s 伸びた
- 原因の候補 (どちらも推測。今回の計測では切り分けられない)
  - (a) nginx がディスクから画像を読むとき、ワーカーが止まる。asia1 は2コアで nginx のワーカーは2つ。`aio` を設定していないので、sendfile でページキャッシュに無いファイルを読むと、その間ワーカーが受け持つ全接続 (API の転送を含む) が止まる。Go のアプリなら止まるのは1ゴルーチンだけ。#19113 で、asia1 のページキャッシュが小さく、投稿画像がすぐ追い出されることがわかっている
  - (b) デプロイ時の chmod の書き戻しが残っていた。開始直後の kworker は確認できたが、t≈52〜60 に kworker は出ていない
- 原因箇所: `etc/nginx/sites-available/isureal.conf` の `location /_images/`、`go/image_api.go` の AccelPath の分岐
- 対策案: 最新の main (#56 で投稿画像をメモリに置く) を取り込み、`imageDataCache` にある画像はアプリから返し、無いときだけ X-Accel-Redirect にする。internal location に `aio threads;` を入れる
- 期待効果: 小〜中。#56 の後では、ディスクから読む画像 (初期データ、追い出された画像) だけが nginx に回る
- リスク: キャッシュを先に見るので、ファイルのある画像の判定順が変わる。中身は同じなので応答は変わらない

### 2. エクスポートと内部 API でのファイル読み込み
- 根拠: asia1 の pprof で `ImageStore.load` 5.18s (11.8%)、そのうち `readImageFile` 5.04s。呼び出し元は exportPostsHandler (7.19s) と europe1 / america1 から来る内部 API。getImageHandler は X-Accel-Redirect で上位から消えた
- 原因箇所: `go/image_store.go` の load / readImageFile
- 対策案: #56 のキャッシュで、新しい画像の分は減る見込み。初期データの画像はエクスポートのたびにディスクから読む
- 期待効果: 小 (#56 との重なりを確かめる必要がある)
