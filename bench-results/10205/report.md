## ボトルネック上位

### 1. 画像の INSERT (DB)
- 根拠: 1,330回、平均 117.93ms、DB 時間の 33.7% (#8691: 997回 / 123.94ms / 30.0%)
- 原因箇所: `go/post_api.go:90`
- 対策案: #8691 の報告の 1 と同じ (画像を DB から剥がす)
- 期待効果: 大

### 2. 投稿期間の行ロックの待ち (投稿と投稿期間の作成の競合)
- 根拠: `SELECT id, local_date, starts_at FROM posting_windows WHERE region = $1 AND ended_at IS NULL FOR SHARE` が 1,352回、平均 **20.78ms**、合計 28.1秒、DB 時間の 6.0% (#8691: 1,007回 / 1.80ms / 1.8秒)
- 原因箇所: `go/post_api.go:109`。投稿は今の投稿期間の行を FOR SHARE でロックし、投稿期間の作成は `go/admin_posting_window_api.go:61` の `UPDATE posting_windows SET ended_at` でその行をロックしたまま、通知の INSERT とコミットまで進む
  - asia の期間を開いている間 (最大 3.39s)、asia の投稿はこのロックで待たされる。反対に、投稿期間の作成も、実行中の投稿のロックが外れるのを待つ
  - #8691 は asia の利用者が少なく (1期間に十数件)、この待ちが目立たなかった。今回は asia の1期間に最大 312件の投稿がある
- 対策案: 投稿期間の作成で、古い期間の行をロックしている時間を短くする。例えば、通知の INSERT を、古い期間を終わらせる UPDATE より前に済ませる。ただし `posting_windows_one_active_region` (リージョンごとに終了していない期間は1つ) の一意インデックスがあるため、順番を入れ替えるには工夫が必要
- 期待効果: 中。asia の利用者が多いベンチで効く
- リスク: 投稿と期間の終了の前後関係 (終わった期間には投稿させない) を崩さないこと

### 3. export のクエリ (DB)
- 根拠: 145回、平均 534.51ms、DB 時間の 16.6% (#8691: 155回 / 498.48ms / 18.8%)
- 原因箇所: `go/export_api.go:30-37`
- 対策案: #8691 の報告の 2 と同じ
- 期待効果: 中〜大

### 4. 投稿期間の作成 (通知の INSERT) の残り
- 根拠: 通知の INSERT は 16回 / 平均 442.67ms と 2回 / 平均 1196.44ms。asia の admin の最大は 3.39s で、INSERT 以外 (2 のロック待ち) が残りの大半と考えられる (推測)
- 原因箇所: `go/admin_posting_window_api.go:71-79`
- 対策案: 自前で追加した `notifications_user_created_id` を消す (#8691 の3番の追記の案B)。2 の対策と合わせて考える
- 期待効果: 小

### 5. ユーザー検索 (DB)
