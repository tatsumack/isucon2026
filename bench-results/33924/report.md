## 概況

- **検索の SQL は DB から消えた。** #32078 の 3,674回 / 10.2s (DB 時間の 8.8%) が、今回は slow.txt の上位24件に入らない (置き換えたブロック相手の取得と主キー検索は、どちらも1本あたり合計約1.1s未満)
- **代わりに asia1 の CPU を使った。** pprof で `(*UserSearchIndex).candidates` が cum **3.41s (asia1 の CPU の 7.0%)**、flat 0.98s。中身は `strings.Contains` (`memeqbody` 1.47s、`indexbody` 0.83s)。3,463回の検索で1回あたり約1ms。ヒットが51件に届かない検索は、約6,500人を全件走査する

- **asia1 の `/api/users` は速くならなかった。** 平均 1.373s → 1.436s。応答時間のほとんどは優先制御の「その他」枠の待ちで、SQL の 2.76ms を消しても変わらない、という仮説を裏づけた

## ボトルネック上位

### 1. メモリ検索の全件走査が asia1 の CPU を使う

- 根拠: pprof の `(*UserSearchIndex).candidates` が cum 3.41s (7.0%)。asia1 の `/api/users` は平均 1.436s で、#32078 (1.373s) から改善なし
- 原因箇所: `go/user_search_index.go:162` (`candidates`)。ヒットが少ないと、6,500件を `strings.Contains` で2回ずつ判定する
- 対策案: 変更を取り下げて SQL に戻す (推奨)。続けるなら、トライグラムの転置索引で候補を絞る、検索語ごとの結果のキャッシュ、などで1回 0.1ms 以下にする必要がある
- 期待効果: 大。asia1 の CPU を 7% 空け、#32078 の状態に戻す
- リスク: なし (元に戻すだけ)

### 2. ピーク時の asia1 の CPU 不足

- 根拠: vmstat の t=55〜100s で idle 3〜16%。flat の上位は `Syscall6` 11.68s (23.9%)、`sha256.blockAVX2` 4.09s (8.4%)
- 原因箇所: `go/image_signature.go:73` (`computeImageSignature` cum 4.95s)、ネットワーク I/O
- 対策案: 画像の署名をキャッシュする、syscall の内訳 (`go tool pprof -peek Syscall6`) を見て書き込み回数を減らす
- 期待効果: 大。critical の待ちと、最後の期間の asia の投稿数に効く
- リスク: 署名の有効期限、画像削除の5秒ルール

### 3. 友達フィードのクエリが #32078 の2倍遅い

- 根拠: `WITH me AS ...` が平均 1.14ms → 2.19ms、合計 21.0s → 35.2s。asia2 のピーク時の idle が 0〜8%
- 原因箇所: `go/post.go:118` の友達フィードの SQL
- 対策案: まずベンチの再実行でぶれかどうかを確かめる。再現するなら `EXPLAIN (ANALYZE, BUFFERS)` で実行計画を確認し、`/initialize` の後の `ANALYZE` を検討する
- 期待効果: 中。投稿→フィードの p90 (0.59s → 1.74s) に効く
- リスク: 小
