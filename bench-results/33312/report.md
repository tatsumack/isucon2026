# ベンチ #33312 (PR #76 asia1 のセッション認証をキャッシュする)

- ブランチ: `perf/session-auth-cache` (`73ba62b`)。main (`97ee54a`、#73 を含む) に、#76 の変更を加えたもの
  - asia1 でだけ、セッションの認証結果をプロセス内にキャッシュする (`ISUREAL_SESSION_CACHE=1`)
  - 4台とも `73ba62b`。asia1 の env に設定が入っていること、DB との接続が TLS 無しのままであることをデプロイ後に確認した
- 比較の基準: #32078 (#73、151161)
- 計測: 08:16:58 UTC からの150秒 (4台)。計測の失敗は無い
- 結果: **score 148887**。#32078 から **-1.5%**。ベンチ1回ずつの比較なので、ぶれを含む
- Stdout: `stdout.txt`。エラーメッセージが2件ある (下の「エラー」)

## 結論

- **キャッシュは効いている**
  - asia1 の pprof で `getSessionFromHeader` が 2.60 → 0.49s になった
    - キャッシュを引く処理 (`SessionCache.lookup`) が 0.33s 増えた
    - 差し引き約1.8s、asia1 の CPU の約3.6%
  - DB からセッションのクエリ (`login_sessions` の JOIN、#32078 で 58,961回) が無くなった
- **スコアは上がらなかった**
  - asia の人数は過去最多: 4日目 410 → 480人、5日目 1,158 → **1,281人**
  - しかし asia の最後の期間の投稿は 572 → **466件**、グランプリは 564 → **463人** に減った
  - asia1 は張り付いたまま (計測開始から 55〜80秒で idle 3〜17%)。人数が増えた分、最後の期間の負荷がさらに高い
    - 「その他」の平均の待ちは 08:18:13 に 4.3s、08:18:23 に 5.9s (#32078 は 3.8s / 4.1s)
    - 重い API の平均の待ちは、最大 20.0s
- **判断: キャッシュはマージしてよい。ただしスコアの差はぶれの範囲と見ている (推測)**
  - CPU と DB の処理が減ったことは計測で確かめた
  - 人数が増えたことと、最後の期間の投稿が減ったことは、ぶれと負荷の両方が考えられる。切り分けていない
- **別件: DB の接続数が上限に近い**。初めて `too many clients` の 500 が出た (下の「エラー」)

## エラー

### 1. `GET /api/posting-window/current` が 500 (`too many clients already`)

- asia1 で 08:18:11 に1件
- PostgreSQL の上限は `max_connections = 100`。そのうち3本は superuser 用 (`superuser_reserved_connections = 3`) なので、アプリが使えるのは97本
- ベンチの後の接続数 (asia2 の `pg_stat_activity`)
  - europe1: 31本、すべて idle (プール30 + LISTEN 1)
  - america1: 31本、すべて idle
  - asia1: 21本 + isureal-guard 1本
- 各台のプールは最大30本 (`go/server.go:39-40`、`SetMaxOpenConns(30)` / `SetMaxIdleConns(30)`)
  - 3台で 90本 + LISTEN 3本 + isureal-guard 1本 = **94本**。上限の97本まで3本しかない
- 上限を超えた理由は確かめていない
  - 切断されたリクエストで捨てられた接続の代わりを開くとき、古い接続のプロセスがまだ残っていて、一時的に数が超えたと見ている (推測)
- 対策案
  - europe1 / america1 のプールを小さくする。この2台は API の大半を asia1 に転送しているので、30本は要らない (推測)
  - または `max_connections` を上げる
- #32078 以前のベンチでは出ていない。このブランチの変更 (セッションのキャッシュ) は接続数を変えていない
