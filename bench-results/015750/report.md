# ベンチ #015750 分析（score 未確認、ブランチ worktree-fix-posting-window-lock）

計測上の制約: ベンチ開始後に計測を開始したため、主要な負荷区間を取り逃している。70秒間のアプリCPUサンプルは各ホスト 0.5〜0.59 CPU秒、アクセス数も主要APIで数十件に留まった。この結果は変更の方向性確認には使えるが、最大負荷時のボトルネック判定には再計測が必要。

## 概況

- ボトルネックの所在: 計測区間ではCPU・I/Oとも余裕があり、飽和はない。アプリCPUは各ホスト平均 0.81〜1.04%、DBのpostgresプロセスも合計約1%で、vmstatのiowaitはasia2平均0.6%。
- インデックス追加の効果: 前回 #940 の画像取得SQLは835回・total 364秒・mean 436msだった。今回は61回・total 2.20秒・mean 36.10msまで低下した。呼び出し量が違うためtotalは単純比較できないが、meanは約92%短縮している。
- usersテーブルロック撤去の効果: 前回上位だった `LOCK TABLE users IN SHARE ROW EXCLUSIVE MODE` と posting window のロック待ちは、今回のpg_stat_statements上位20件から消えた。ただし投稿期間開始を十分含む負荷区間ではないため、効果の確定には再計測が必要。
- リージョン間差は残る。`GET /api/memories` はasia1平均15msに対し、europe1 1.043秒、america1 1.114秒。`GET /api/images/:id` もasia1 13msに対し、europe1 529ms、america1 638msで、遠隔DBへの逐次往復が支配的。
- `/api/notifications` の60秒はSSEの接続時間であり、そのまま遅いAPIとは扱わない。今回の4XXは計測区間終了付近の切断を含む可能性がある。

## ボトルネック上位

### 1. europe/americaから共有DBへの逐次往復

- 根拠: `GET /api/memories` 平均 asia1 15ms / europe1 1.043秒 / america1 1.114秒。画像取得も13ms / 529ms / 638ms。pprofでもeurope1は `database/sql.(*DB).QueryContext` 累積250ms、america1は210msで、低負荷中もDB待ちが目立つ。
- 原因箇所: `go/memory_api.go:73` の `listMemories` は投稿一覧取得後、`go/memory_api.go:98` の `loadMemoryInteractions` で追加クエリを発行する。認証・ユーザー取得を含め、リクエスト内で複数回DBへ往復する。
- 対策案: memoriesで必要なデータをまとめて取得し、認証ユーザー情報など安全に短時間キャッシュできるものを検討する。まず遠隔リージョンの1リクエスト当たりSQL回数を計測する。
- 期待効果: 大。遠隔リージョンではSQLを1往復減らすごとに概ねネットワークRTT分を削減できる。
- リスク: 中。クエリ統合でレスポンス順序・空配列・削除済みデータの扱いを変えないこと。キャッシュは退会・プロフィール更新時の無効化が必要。

### 2. 画像取得SQLは改善したが依然DB時間の65.2%

- 根拠: 61回・total 2,202ms・mean 36.10msで、計測区間のDB実行時間の65.2%。前回mean 436msから大幅改善したが、呼び出し頻度が上がる本負荷では引き続き主要コストになる。
- 原因箇所: `go/image_api.go:70-86` のposts/realmojisを確認するEXISTS。追加済みの `sql/002-performance-indexes.sql:28-30` と `:51-53` でフルスキャンは解消されたと考えられる。
- 対策案: 正しい負荷区間で `EXPLAIN (ANALYZE, BUFFERS)` を取得し、複合条件に合わせたindex-only化の余地を確認する。アプリ側で署名済み画像URL生成・同一画像の重複取得も確認する。
- 期待効果: 中。meanは既に大きく改善済みだが、画像取得回数が多いため残余コストの削減価値はある。
- リスク: 小〜中。画像の削除・投稿削除・ユーザー退会を即時反映する認可条件をキャッシュで壊さないこと。

### 3. エクスポートが1回で約996ms、画像データ185件をDBから取得

- 根拠: pg_stat_statements 2位。1回・total/mean 995.69ms・185 rows・DB時間の29.5%。
- 原因箇所: `go/export_api.go:30-37` がユーザーの全投稿と画像byteaを一度にJOIN取得し、`go/export_api.go:41` 以降でZIPをメモリ上に構築する。
- 対策案: エクスポートがベンチの採点経路なら、DB取得とZIP生成をストリーミング化するか、少なくとも画像を含む大きな結果セットの全保持を避ける。採点上の頻度が1回だけなら優先度は下げる。
- 期待効果: 中。単発レイテンシとメモリピークは下がるが、全体スコアへの寄与は呼び出し頻度次第。
- リスク: 中。ZIPのファイル順、ファイル名、レスポンス形式を維持する必要がある。

### 4. 通知ポーリングでユーザー取得が大量に発生

- 根拠: users取得は2,664回だがtotal 42ms、notifications取得は2,654回でtotal 34ms。DB単体は高速になった一方、遠隔リージョンでは各ポーリングのネットワーク往復が累積する。pprof累積では通知ハンドラがasia1 190ms、europe1 250ms、america1 200ms。
- 原因箇所: `go/notification_api.go:38-56` で500msごとにユーザーと通知をDBから取得する。
- 対策案: 接続中に不変なユーザー属性の再取得を減らし、通知発生の合図だけを共有する仕組みを検討する。複数リージョン間で通知を落とさない設計が必要。
- 期待効果: 中。DB実行時間より遠隔往復数の削減に効く。
- リスク: 大。退会・リージョン変更・複数アプリサーバ間の通知整合性に注意。

### 5. posting windowのテーブルロック撤去は有望だが再検証が必要

- 根拠: 前回はusersテーブルロック44回・mean 2,159ms、posting_windowsロック150回・mean 902msだったが、今回は上位20SQLに現れない。
- 原因箇所: `go/admin_posting_window_api.go:46-48` でusersテーブルロックをリージョン単位のtransaction advisory lockへ置換済み。
- 対策案: 次回はベンチ開始前から計測し、投稿期間開始時のSQL待ち時間、POST /api/postsのP95、リージョン別成功数を確認する。
- 期待効果: 大の可能性。以前の主要ロック競合を除去している。
- リスク: 中。投稿期間開始と退会・登録の並行時に、通知対象のスナップショットが仕様を満たすことを確認する。
