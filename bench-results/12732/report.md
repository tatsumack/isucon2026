## ボトルネック上位

### 1. asia1 の CPU (画像署名)
- 根拠: pprof の 62.9% が `computeImageSignature` (SHA-256 の `blockAVX2` が 48.4%)。呼び出し元は `listMemories` が 42.2%、`newPostResponse` が 35.4%、`newRealMojiResponse` が 26.9%。asia1 の idle は 150秒平均 57.5% で、idle 5% 未満が 42秒。europe1 / america1 の idle は 93.5% / 94.3%
- 原因箇所: `go/image_signature.go:68` (`computeImageSignature`)、`go/image_signature.go:107` (`signedImageURL`)
- 対策案: #11801 の1番と同じ。署名の計算を、CPU に余裕のある europe1 / america1 に任せる。Memories や投稿の応答で返す署名の数を減らす
- 期待効果: 大。asia に利用者が偏る負荷では、asia1 の CPU が上限を決めている
- リスク: 署名の値と有効期限の形式は変えてはいけない

### 2. 画像の閲覧権限の確認クエリ (DB)
- 根拠: `SELECT u.secret_key_hash, i.media_type, (u.profile_image_id = i.id OR EXISTS (...))` が 8,514回、平均 1.86ms、合計 15.8秒、DB 時間の 15.2% (#11801: 7,873回 / 1.95ms / 12.1%)
- 原因箇所: `go/image_api.go`
- 対策案: 画像の取得ごとに DB に聞かず、署名の検証と、プロセス内キャッシュで済ませる。無効化は、画像の削除・投稿の削除・プロフィール画像の変更・RealMoji の削除の4か所
- 期待効果: 中。DB 時間の15%だが、1回が短いので、asia1 の CPU 時間のほうが効いている可能性がある
- リスク: 閲覧権限 (削除後5秒以内に見えなくなること) を崩さない

### 3. 友達フィードのクエリ (DB)
- 根拠: `WITH me AS (...), friends AS (...)` が 6,970回、平均 1.77ms、合計 12.4秒、DB 時間の 11.9% (#11801: 8,634回 / 1.21ms / 8.2%)
- 原因箇所: `go/post.go:118`
- 対策案: 友達の一覧をプロセス内に持つ。または、クエリを1回の往復にまとめる
- 期待効果: 小〜中。友達フィードの検証通過 (1件10点) に直結するので、遅くしてはいけない
- リスク: 友達の追加・削除・ブロックの直後に反映される必要がある (キャッシュは、これらの書き込みで無効化)

### 4. 友達申請の承認のロック (DB)
- 根拠: `SELECT id FROM users WHERE id IN ($1, $2) AND status=$3 ORDER BY id FOR NO KEY UPDATE` が 3,846回、平均 2.77ms、合計 10.6秒、DB 時間の 10.2% (#11801: 3,930回 / 2.98ms / 9.2%)。同じ形で `status` の条件なしのものも 271回 / 5.79ms
- 原因箇所: `go/relationship.go:38` と `go/relationship.go:52` (2人の users 行を `FOR NO KEY UPDATE`)
- 対策案: 2人の users 行の `FOR NO KEY UPDATE` が、1回 2.8ms と、1行の主キー参照にしては遅い。同じユーザーへの申請が集中して、ロック待ちが出ている可能性がある (推測)。`pg_locks` で待ちの相手を確認してから、ロックの範囲を見直す
- 期待効果: 小〜中
- リスク: 友達申請の二重承認や、ブロックとの前後関係を崩さない

### 5. ユーザー検索 (DB)
- 根拠: `SELECT ... FROM users WHERE status=$5 AND id<>$1 AND (... search_username LIKE $4 OR ...)` が 1,024回、平均 7.51ms、合計 7.7秒、DB 時間の 7.4% (#11801: 1,140回 / 10.69ms / 9.6%)
- 原因箇所: `go/user_read_api.go:82`
- 対策案: `pg_trgm` の GIN インデックスを `search_username` / `search_display_name` に付ける。実行計画 (`EXPLAIN`) を先に見る
- 期待効果: 小〜中
- リスク: インデックスの作成に時間がかかる可能性があるので、`/initialize` と追試の再起動後も保たれることを確認する
