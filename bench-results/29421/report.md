# ベンチ #29421 (PR #71 asia1 の優先制御で、画像の取得を専用の枠にする)

- ブランチ: `perf/priority-image-group` (`f57c6ed`)。main (`a218a7d`、#69 を含む) に、#71 の変更を加えたもの
  - asia1 の `split` の優先制御で、`GET /api/images/:imageId` を「その他」の枠から外す
  - 画像には専用の8枠を用意する (`ISUREAL_PRIORITY_IMAGE_LIMIT=8`)
  - 4台とも `f57c6ed` で、asia1 の env に設定が入っていることを確認した
- 比較の基準: #28870 (main + #69 と同じ中身、138429)
- 計測: 07:38:20 UTC からの150秒 (4台)。計測の失敗は無い
- 結果: **score 136072**。#28870 から **-1.7%**。ベンチ1回ずつの比較なので、ぶれを含む
- Stdout: `stdout.txt`。エラーメッセージは無し

## 結論

- **画像の取得は大きく速くなった**
  - asia1 の `GET /api/images` は、平均 1.286 → **0.023s**、p99 7.77 → 0.25s
  - asia1 のディスクの読み込み (vmstat bi) は 2,587 → 968MB、iowait (平均) は 17.0 → 6.2%
  - 読み込みが減ったのは、待たされた画像のリクエストの切断と再試行が減ったためと見ている (推測)。画像の 4xx は 785 → 263件
- **狙った「その他」の API は速くならなかった**
  - 優先制御のログで、「その他」の待ちは、最後の期間に平均 2.0s → 4.4s まで伸びた
  - asia1 の API (#28870 → #29421)

    | API | #28870 | #29421 |
    |---|---|---|
    | `POST /api/friend-requests` | 1.498s | 1.584s |
    | `GET /api/users` | 1.574s | 1.743s |
    | `GET /api/memories` | 1.675s | 2.030s |
    | `GET /api/me` | 2.997s | 2.757s |

  - 投稿の経路 (critical) も待つようになった。07:39:25 に平均 315ms、07:39:45 に 244ms
  - **「その他」が詰まる原因は、画像との取り合いではなく、asia1 の CPU が足りないことだった**
    - 張り付く区間 (計測開始から 54〜86秒) は、idle 3〜21%、wa 7〜24%
    - 画像に8枠を足したので、同時に動く数が増えた。その分、ほかの処理が使える CPU が減った可能性がある (推測)
- **asia の投稿は減った** (#28870 → #29421)
  - 5日目の期間: 424 → 372件
  - 最後の期間: 435 → 399件
  - グランプリ: 434 → 395人
  - 5日目の人数はほぼ同じ (982 → 978人) で、asia1 で投稿まで進めた人が減った
- **判断: このままではマージしない方がよい**
  - 画像の高速化は得点に結びついていない
  - asia の投稿が減ったことは、ぶれの可能性もある。ただ、少なくとも狙った改善 (「その他」の待ちが減る) は起きていない
