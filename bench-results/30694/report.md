# ベンチ #30694 分析 (score 131598) — ブランチ tatsumack/TCPの設定変更 (9fe4ad9)

施策: asia1 / europe1 / america1 で `tcp_slow_start_after_idle=0`、`tcp_rmem` 初期値 1MB、192.168.0.0/16 の経路に `initcwnd 64 initrwnd 64`。
比較対象: main の #28870 (138429)。**結果: スコアは上がらなかった。この設定はベンチ後にサーバから外した (main には入れない)**

計測の注意
- bench-capture は 07:51:07 UTC から150秒。ベンチは 07:51:35〜07:54:06 なので、最後の約30秒 (グランプリ以降) は alp / pprof / vmstat に入っていない
- `ss-europe1.txt` / `ss-america1.txt` は asia1 (192.168.1.10) への接続の cwnd / 再送を5秒ごとに取ったもの。retrans はその時点で開いている接続の累計の合計。#28870 では取っていないので、再送の数は前回と比べられない

- 初期ウィンドウを広げると、負荷が小さいとき (america、通常の期間) の投稿は速くなる。一方で、多くの接続が同時に送る負荷の山では europe1 がパケットを落とし、遅くなった (推測。原因を確かめる計測はしていない)
- 次に打つ施策: initcwnd を 16〜32 に下げる、または fq + BBR で送る速さをならす。どちらも試していない

## ボトルネック上位
### 1. 負荷の山で europe1 → asia1 の転送が詰まる
- 根拠: ss-europe1.txt (520本、再送 約1万件)、europe1 の POST /api/posts の p90 5.52s
- 原因箇所: サーバの TCP 設定 (アプリのコードではない)。転送は go/delegate.go
- 対策案: initcwnd を下げる / fq + BBR で送る速さをならす / 転送する画像を小さくする
- 期待効果: 中。europe の最後の期間の未完了 (2670点) が減る
- リスク: 帯域制限を「回避」する設定ではないが、レギュレーションの「通信遅延、帯域制限を変更または回避すること」の禁止とどう関係するかは、チームで確認する
