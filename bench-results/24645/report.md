## ボトルネック上位 (スコアへの効果が大きい順)

### 1. asia1 の画像の読み込み (iowait)

- 根拠
  - 張り付く区間の wa は 16〜39%
  - isureal のディスクからの読み込みは 1,365MB / 150秒 (pidstat -d)
  - nginx と journald の書き込みはほぼ無くなった (9MB / 6MB)
  - `GET /api/images` は 8,716回、平均 0.333s
- 原因箇所: 画像の配信 (`go/image_api.go`、`go/image_store.go`)
  - 初期データの画像 (16GB) は、ページキャッシュ (約300MB) にもアプリのキャッシュ (256MB、#56) にも入りきらない
  - Memories の後に見る前日の画像も読み直している (#21908 の分析、推測)
- 対策案
  - 読み込んだ画像の出どころ (初期データ / 新しい投稿) を数え、どちらが多いかを先に確かめる
  - 初期データ側が多い場合は、署名の検証と配信を europe1 / america1 に回す余地を見る。この2台は idle 95% で、画像はルーター経由で asia1 から取る
  - 新しい投稿側が多い場合は、キャッシュの上限を上げる (asia1 のメモリとの兼ね合い)
- 期待効果: 中〜大。asia 4日目の完了率が上がれば、5日目の人数が増える
- リスク: キャッシュを増やすと asia1 のメモリが足りなくなるおそれ (3.8GB で、kcompactd が CPU 2% を使っている)

### 2. アップロードの読み込み (readUpload 11.9%)

- 根拠: pprof の `readUpload` は 6.27s (11.85%)。中身は `bytes.(*Buffer).ReadFrom` と syscall。#24003 は 11.98% で、`read_all.go` の変更の効果は見えない
- 原因箇所: `go/upload_buffer.go` の `readUpload`。投稿とプロフィール画像の本体を受け取る処理
- 対策案: syscall の回数を減らす。例えば、ソケットから読むバッファを大きくする。中身の内訳は `go tool pprof -list readUpload` でまだ見ていない
- 期待効果: 小〜中

### 3. プロフィール画像の変更 (10.3%) と export (9.6%)

- 根拠
  - `PUT /api/me/profile-image`: asia1 で393回、平均 0.681s、最大 7.1s。4xx が134件
  - `GET /api/me/export`: 151回、平均 0.905s
- 対策案
  - プロフィール画像: 400 になる不正な画像を、本体を読み切る前に返せないか見る (4xx は加点されない)
  - export: 張り付く区間 (t≈43〜60) に来ている件数を数え、ずらせない処理かを確かめる
- 期待効果: 小〜中
