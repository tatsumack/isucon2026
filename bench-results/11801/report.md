## ボトルネック上位

### 1. asia1 の CPU (画像署名)
- 根拠: 後半は CPU の idle が0〜3%。pprof の 63.0% が `computeImageSignature`、うち `listMemories` が 42.0%
- 原因箇所: `go/image_signature.go` の `computeImageSignature`。呼び出しは `go/memory_api.go`
- 対策案: 署名の計算を europe1 / america1 に任せる (CPU は idle 96〜98%、SHA-NI があり asia1 の約3.3倍速い。#7477 の報告を参照)。Memories で返す署名を減らす
- 期待効果: 大。asia のユーザーが増えた今は、asia1 の CPU が上限を決めている
- リスク: 署名の値と期限の形式は変えてはいけない

### 2. 最後の期間の通知を受け取れない (SSE)
- 根拠: asia のユーザーが期間の開始の2.7〜5.4秒後に SSE へつなぎ、最後の期間の通知を受け取れなかった。グランプリ アジア 0人
- 原因箇所: `go/notification_api.go` (つないだ時刻より後の通知だけを届ける)
- 対策案: まず元の実装 (チームで変える前) の SSE が、つなぐ前の未読の通知を届けていたかを確かめる。仕様上届けてよいなら、開いている期間の通知を、つないだ直後に届ける
- 期待効果: 大 (最後の期間は1件20点)。ただし 1 で asia1 が速くなれば、遅れてつなぐこと自体が減る
- リスク: 通知の仕様 (マニュアル) の確認が必要。推測で変えない

### 3. asia1 の画像ファイルの読み込み (ディスク I/O)
- 根拠: asia1 の iowait は後半 10〜25%、読み込み 16MB/s。asia1 の画像の取得の平均は 0.017s → 0.116s
- 原因箇所: `go/image_store.go` の `load`。初期データの画像 16GB がページキャッシュに収まらない
- 対策案: Memories や export でよく読まれる画像の傾向を調べる。メモリのキャッシュ (256MB) の大きさや追い出し方を見直す
- 期待効果: 中
- リスク: メモリ (asia1 は使えるメモリ 2.3GB)

### 4. export (asia1 へ転送)
- 根拠: asia1 で平均 1.249s (#8691: 0.543s)、europe1 / america1 で平均 3.98s / 3.65s。DB のクエリは 41.5ms に減ったので、画像ファイルの読み込みと asia1 の CPU 待ちと考えられる (推測)
- 原因箇所: `go/export_api.go`
- 対策案: 3 と同じ。ZIP をストリーミングで返す
- 期待効果: 小〜中 (1件20点だが件数は少ない)
