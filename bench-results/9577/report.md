## 結論

- **PR #40 はこのまま merge しないほうがよい**。狙った export SQL は、#8691 の平均 498.48ms から **745.70ms (+49.6%)**、合計 77.3s から **123.8s (+60.2%)** に悪化した
- asia1 の `GET /api/me/export` も平均 0.543s → **0.917s (+68.9%)**、p99 2.024s → **4.240s (+109.5%)**。SQL と HTTP の両方で悪化しており、単なるスコアのぶれだけでは説明できない
- PR 本文の単体 EXPLAIN では改善していたが、実ベンチでは複数ユーザーの export と投稿・画像 INSERT が並行する。`LATERAL ... LIMIT 1` が投稿ごとにパーティション化された `image_objects` を引く形になり、実負荷では効率化できていない可能性がある (推測)
- スコア差のすべてを PR #40 のせいにはできない。今回のグランプリ人数は asia 47 / europe 99 / america 36 で、#8691 の 18 / 191 / 162 と配役が大きく異なる。また、最後の asia 期間で70投稿を期間内に処理しきれなかった

## ボトルネック上位

### 1. export のクエリ (DB)
- 根拠: 166回、平均745.70ms、合計123.8s、DB時間の21.7%。#8691より平均49.6%悪化
- 原因箇所: `go/export_api.go:30-46` (PR #40)
- 対策案: PR #40 は保留。実ベンチ相当の並行条件で実行計画を取り、画像IDをまとめて取得する2クエリ方式などと比較する
- 期待効果: 大。今回の変更対象であり、回帰を戻すだけでもDB時間を約46秒削減できる計算

### 2. 画像の INSERT (DB)
- 根拠: 1164回、平均115.65ms、合計134.6s、DB時間の23.6%。最大のDB負荷
- 原因箇所: `go/post_api.go:90` など
- 対策案: 前回レポート同様、画像本体をDBから剥がす案を検討。先に `wait_event` を採り、TOAST・拡張ロック・書き込みのどれが支配的か確認する
- 期待効果: 大

### 3. 投稿期間作成と最後の期間の遅延
- 根拠: 管理者API最大6.69s、通知 INSERT 平均887.73ms。最後のasia期間は161投稿中91件しか完了しなかった
- 原因箇所: `go/admin_posting_window_api.go:72`
- 対策案: 全ユーザー分の通知行を同期作成しない設計を検討する
- 期待効果: 中〜大。最後の期間は1投稿20点

### 4. 画像署名の計算 (asia1 CPU)
- 根拠: asia1 pprof の `computeImageSignature` が累積48.75s (64.5%)。asia1 のアプリCPUは平均51.2%
- 原因箇所: `go/image_signature.go` の `computeImageSignature`
- 対策案: europe1 / america1 へ計算を分散する。署名値と期限形式は維持する
- 期待効果: 中

### 5. 画像本体の読み込み (DB)
- 根拠: 7244回、平均6.32ms、合計45.8s、DB時間の8.0%。export以外でも画像本体の読み込みが残る
- 原因箇所: `go/image_api.go`
- 対策案: 画像本体のファイル化・各リージョンへのキャッシュを検討し、配信可否のDB確認は残す
- 期待効果: 中
