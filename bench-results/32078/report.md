# ベンチ #32078 (PR #73 DB との接続で TLS を使わない)

- ブランチ: `perf/db-sslmode-disable` (`b027759`)。main (`852cec1`) に、#73 の変更 (DSN に `sslmode=disable`) を加えたもの
  - main の `852cec1` には #72 が入っている。#48 (画像の所有者を `image_owners` から引く) と、#64 のうち投稿時の遠隔署名を取りやめた残り
  - 4台とも `b027759`。asia2 の `pg_stat_ssl` で、3台からの接続がすべて `ssl = f` になったことをデプロイ後に確認した
- 比較の基準: #28870 (main + #69、138429)
  - **main `852cec1` だけのベンチは無い**。今回の差には #48 の効果も入っている。#72 のブランチ (`cdaf87b`) の #30207 は 131600 だが、これは投稿時の遠隔署名を含む
- 計測: 08:04:57 UTC からの150秒 (4台)。計測の失敗は無い
- 結果: **score 151161**。#28870 から **+9.2%**、#29421 (136072) から +11.1%
- Stdout: `stdout.txt`。通信の失敗のメッセージが2件ある (下の「エラー」)

## 概況

- **TLS の処理は無くなった**
  - asia1 の pprof で、`crypto/tls.(*Conn).Write` 3.24s と `Read` 2.25s (#28870) が、今回は出てこない
- **asia1 は同じ CPU で、より多くのリクエストを処理した**
  - pprof の合計: 48.6s → 50.5s。ほぼ同じ
  - asia1 の処理件数 (#28870 → #32078)
    - 画像: 6,950 → 8,001
    - 友達申請: 3,219 → 4,089
    - 投稿: 1,415 → 1,639
    - Memories: 2,076 → 2,382
  - 平均の応答時間は、ほぼ同じか少し短い (友達申請 1.498 → 1.408s、ユーザー検索 1.574 → 1.373s)
- ボトルネックは引き続き asia1 の CPU
  - 張り付く区間 (計測開始から 60〜85秒) は、idle 4〜12%、wa 11〜18%
  - 150秒の平均は id 54.9 → 68.7%、wa 17.0 → 7.1%。ただし #28870 は計測の最後の35秒に wa 30〜40% の区間があり、そのまま比べられない
- **asia2 の負荷は下がった**
  - postgres の CPU (pidstat の平均) は 57 → 45%
  - DB の時間の合計 (slow.txt から概算) は約175s → 約115s
  - 主な理由は #48。画像の所有者を引くクエリが 41.1s (平均 2.97ms) → 7.4s (0.48ms) になった
  - ユーザー検索のクエリも 25.5s (7.36ms) → 10.2s (2.76ms) になった。DB が空いた分、速くなったと見ている (推測)
- **TLS をやめた分と、#48 の分は切り分けられていない**
  - TLS で減るのは asia1 の CPU (#29421 で暗号化と復号が2〜3%、syscall を含めて約11%) と asia2 の CPU
  - スコアの増え方 (+9.2%) は、TLS だけでは大きすぎる (推測)。#48 の効果が大きいと見ている

## ボトルネック上位 (スコアへの効果が大きい順)

### 1. 投稿 (17.7%)
- 根拠: `createPostHandler` 8.92s。内訳は次の3つ
  - 画像の署名 (`newPostResponse`) 3.52s
  - 画像の保存 (`ImageStore.Save`) 2.47s。うち `writeFileAtomic` の fsync が 2.03s
  - アップロードの読み込み (`bindCreatePostRequest`) 2.25s
- 対策案
  - 署名は、チームで別途対応中
  - 画像の保存の fsync は #51 が該当する

### 2. 画像の署名 (11.1%)
- 根拠: `computeImageSignature` 5.62s
- 対策案: チームで別途対応中

### 3. export (10.1%)
- 根拠: `exportPostsHandler` 5.11s、うち `writeExportImage` 3.48s。asia1 で133回、平均 1.48s
- 対策案: 画像の書き出しの内訳 (ファイルを開く、コピー) を行単位で見る

### 4. アップロードの読み込み (7.0%)
- 根拠: `readUpload` 3.54s (投稿とプロフィール画像)
- 対策案: sync.Pool のバッファは GC で消える。GC をまたいで残る置き場に替えて、確保とゼロ埋めを減らす

### 5. プロフィール画像 (7.1%)
- 根拠: `putProfileImageHandler` 3.60s。783回、平均 2.49s、4xx が140件
- 対策案: 不正な画像を、本体を読み切る前に 400 で返す
