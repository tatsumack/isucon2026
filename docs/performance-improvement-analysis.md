# ISUReal パフォーマンス改善候補

当日マニュアルとGoリファレンス実装を静的に確認し、改善候補を影響が大きいと考えられる順にまとめる。

実測ログ、`EXPLAIN ANALYZE`、pprofは未確認であるため、以下の順位はコードの静的解析に基づく。実際の着手順は、初期ベンチの計測結果と照合して確定する。

## ルールの要点

- スコアは、成功した活動件数に活動ごとの配点とリージョン倍率を掛けた合計。
  - Asia: 1倍
  - Europe: 1.5倍
  - America: 1.5倍
- 特に配点が高い活動は以下。
  - 投稿後の友達フィード検証: 10点、最後の投稿期間は20点
  - エクスポート: 20点
  - RealMoji送信: 5点
  - コメント投稿: 3点
  - プロフィール画像の変更・削除: 3点
  - 画像取得: 2点
- 通常のエラー件数による直接減点はないが、権限や整合性の違反はベンチマークの即時FAILにつながり、スコアは0点になる。
- 書き込み成功後の読み取りには、リージョンをまたぐ場合も結果を反映する必要がある。
- 投稿削除後、画像を取得できる猶予は最大5秒。
- `/api/initialize`では、全リージョンのデータ、追加したキャッシュ、複製先を含めて初期状態へ戻す必要がある。
- サーバ再起動後にもデータが残り、追試で最終スコアの75%を超える性能を再現する必要がある。
- URI、HTTPメソッド、ステータス、JSONやHTMLの構造と意味、静的ファイル、認証、公開範囲、画像署名の検証結果を維持する。
- ベンチマーカーだけを識別し、本来と異なる応答を返す実装は禁止。
- 固定リージョン、公開先、ルーター経由の通信を維持する。
- 当日マニュアルの記載は一般レギュレーションより優先される。

## 改善候補

### 1. 必要なDBインデックスを追加する

**想定影響: 非常に大 / 難易度: 低〜中**

認証ミドルウェアは、ほぼすべてのAPIリクエストで`login_sessions.token_hash`を検索するが、この列にインデックスがない。

候補となるインデックス:

- `login_sessions(token_hash) WHERE active`
- `administrator_sessions(token_hash) WHERE active`
- `posts(posted_at DESC, id DESC) WHERE deleted_at IS NULL`
- `posts(author_id, posting_window_id) WHERE deleted_at IS NULL`
- `posts(image_id) WHERE deleted_at IS NULL`
- `realmojis(image_id) WHERE replaced_at IS NULL AND deleted_at IS NULL`
- `friendships(user_high_id, user_low_id)`
- `follows(followee_id, follower_id)`
- `block_relations(blocked_id, blocker_id)`
- `friend_requests(recipient_id, status, updated_at DESC, id DESC)`
- `friend_requests(requester_id, status, updated_at DESC, id DESC)`
- `notifications(user_id, created_at, id)`

複合UNIQUEインデックスの先頭列と逆向きの検索や、関係テーブルに対する`OR`条件が多い。実データに対して`EXPLAIN (ANALYZE, BUFFERS)`を取得し、インデックスを1施策ずつ追加して検証する。

関連箇所:

- `go/session.go`
- `go/post.go`
- `sql/001-schema.sql`

### 2. フィードで全投稿を取得してからGoで絞る処理をなくす

**想定影響: 非常に大 / 難易度: 中〜高**

現在のフィードは、アクティブな投稿期間に存在する他人の投稿をLIMITなしで取得し、その後Go上で公開範囲や友達関係を判定する。

`friends-of-friends`ではさらに、全候補について以下を実行する。

- 投稿者の友達関係取得
- 候補投稿のRealMoji・コメント取得
- Go上でスコア計算
- 全候補のソート
- 最後に51件で打ち切り

投稿数が増えるほど1リクエストの処理量が増え続ける。フィードは利用者1人・投稿期間あたり最大20回加点され、投稿後の10点または20点の検証にも使われるため、優先度が高い。

改善案:

1. feed種別ごとにSQLを分ける。
2. 投稿者と公開範囲の条件をSQLへ押し込む。
3. `(posted_at, id)`のカーソル条件と`LIMIT 51`をDB側で適用する。
4. friends-of-friendsのスコアをSQLで集約するか、更新時に事前計算する。
5. 関係情報を再利用できる形にする。

公開範囲の誤りはFAILにつながるため、最適化前後で同じ結果になることをテストする。

関連箇所: `go/feed_api.go`

### 3. 投稿作成時のposting window行ロックを解消する

**想定影響: 非常に大 / 難易度: 中**

投稿作成時に、現在の`posting_windows`行を`FOR UPDATE`でロックしている。同じリージョンの利用者は同じ行を参照するため、リージョン内の投稿処理が直列化される可能性が高い。

投稿は10点または20点の中心活動であるため、共通行ロックは大きなボトルネックになり得る。

改善案:

- 行ロックなしで現在期間を読む。
- INSERT直前または条件付きSQLで、投稿期間がまだ終了していないことを検証する。
- 管理者による投稿期間切り替えとの競合をテストする。

単純に`FOR UPDATE`だけを削除すると整合性を壊す可能性があるため、期間終了との競合を維持できる実装が必要。

コメント、RealMoji、投稿更新などでも利用者行をロックしており、同一利用者の活動が直列化される。まずは全利用者で共有されるposting window行のロックから調べる。

関連箇所: `go/post_api.go`

### 4. Europe/Americaから中央DBへの往復回数を減らす

**想定影響: 非常に大 / 難易度: 高**

現在、Asia、Europe、Americaの全アプリケーションがasia2のPostgreSQLを参照する。EuropeとAmericaは1.5倍の配点だが、各SQLにリージョン間RTTが加わる。

フィードや投稿詳細などでは、1リクエスト中に次のSQLを逐次実行する場合がある。

- セッション取得
- ユーザー取得
- 当日投稿済み判定
- ブロック一覧
- 友達一覧
- 友達の友達一覧
- 投稿一覧
- リアクション集計

最初はJOINやCTEでSQLをまとめ、DB往復数を減らすのが比較的安全。

地域DBへの完全分割は、別リージョンでもread-after-writeが必須なため難易度が高い。先に以下を検討する。

- セッションや変更頻度の低いユーザー情報の短時間キャッシュ
- 関係情報の世代番号付きキャッシュ
- SQLの統合
- 不変な初期画像データのローカルキャッシュ

友達解除、ブロック、公開範囲変更などの成功応答前に全リージョンへ変更が反映されないキャッシュは、FAIL要因になる。

関連箇所:

- `etc/env/*.sh`
- `go/config.go`
- `go/post.go`
- `go/feed_api.go`

### 5. SSEの500msポーリングをイベント通知に変える

**想定影響: 大 / 難易度: 中**

通知エンドポイントは接続ごとに500ms間隔で、利用者・リージョンの取得と新着通知の検索を繰り返す。接続数が増えると、SSEだけで毎秒およそ「接続数 × 4」のSQLが発生する。

一方、DBコネクション上限は各アプリケーションプロセスで30。

改善候補:

- PostgreSQLの`LISTEN/NOTIFY`
- DBを介した通知とアプリケーション内の購読管理
- ポーリング間隔を延ばし、通知生成時に待機処理を起床させる方式

複数アプリケーション間で通知を伝える必要があるため、プロセス内チャネルだけでは不十分。

関連箇所:

- `go/notification_api.go`
- `go/server.go`

### 6. 画像取得を1クエリにし、画像本体をキャッシュする

**想定影響: 大 / 難易度: 中**

画像取得は1件2点で高頻度になると考えられる。現在は1画像につき以下の2クエリを実行する。

1. 所有者のSecretKey取得
2. 削除状態・有効性確認と`bytea`取得

これらは1SQLへ統合できる。また、権限・削除状態の確認をDBで維持しつつ、重い画像バイト列だけをID単位でキャッシュする構成が考えられる。

`image_objects`は月別パーティションだが、通常の検索条件は`id`だけである。IDから対象パーティションまたは作成時刻を引ける小さな索引テーブルも候補になる。

画像を単純にnginxでキャッシュすると、投稿削除後5秒以内という条件やアカウント削除後の扱いを破る可能性があるため、そのまま適用しない。

関連箇所:

- `go/image_api.go`
- `sql/001-schema.sql`

### 7. viewer contextの再構築を減らす

**想定影響: 大 / 難易度: 中**

投稿詳細、フィード、コメント権限、RealMoji権限などで`loadViewerContext`が繰り返し呼ばれる。この関数は毎回以下を構築する。

- 本人情報
- 当日投稿済みか
- ブロック関係
- 友達
- 友達の友達
- 共通の友達数

同一セッション中に再利用される情報が多い。関係変更時に確実に無効化できるキャッシュ、またはDB上の隣接・集約テーブルが有効と考えられる。

関連箇所: `go/post.go`

### 8. ユーザー検索の全件読み込みをなくす

**想定影響: 中〜大 / 難易度: 中**

現在の検索は、カーソル以降の全アクティブユーザーをDBから取得し、Unicode正規化と部分一致をGoで行い、51件見つかった時点で終了する。一致率の低い検索ではほぼ全件を読み込む。

改善案:

- 正規化済み検索列を用意する。
- PostgreSQLの`pg_trgm`とGINインデックスで部分一致検索する。
- 現在のUnicode正規化結果と完全に一致することをテストする。

関連箇所: `go/user_read_api.go`

### 9. Memories・エクスポートのメモリ使用量を抑える

**想定影響: 中 / 難易度: 中**

Memoriesは最大50投稿に該当する全RealMoji・コメントをDBから読み、Go側で投稿ごとに50件へ切っている。SQLのウィンドウ関数を使い、投稿ごとに50件へ絞ってから転送できる。

エクスポートは全画像をDBから読み、ZIP全体をメモリ上に構築してからレスポンスを返す。同時実行時のメモリ圧迫が大きいため、レスポンスへZIPを直接ストリーミングする方式が候補になる。

エクスポートは1回20点であり、処理の優先度自体は高い。ただし、最初にフィード・投稿経路を改善したほうが全体スコアへの寄与は大きいと推測する。

関連箇所:

- `go/memory_api.go`
- `go/export_api.go`

### 10. ログ・nginx・コネクション設定を実測に合わせる

**想定影響: 中 / 難易度: 低**

現状では以下が確認できる。

- Goの既定ログレベルは`debug`
- nginxアクセスログが全件有効
- nginxの`worker_connections`は768
- DB最大接続数は各プロセス30
- 静的ファイルの長期キャッシュ設定が見当たらない
- gzip対象MIME typeがほぼ既定のまま

運用ルール上、ログ出力の停止は行わない。必要な調査能力を維持したうえで、バッファリングや出力量の調整を検討する。

関連箇所:

- `go/action_log.go`
- `go/server.go`
- `etc/nginx/nginx.conf`

## 推奨する着手順

1. 初期ベンチを実行し、`alp`、slow query、pprofで基準値を保存する。
2. 認証・関係・フィード用インデックスを追加する。
3. フィードのSQL絞り込みとLIMIT適用を行う。
4. 投稿期間の共通行ロックを解消する。
5. SSEポーリングを改善する。
6. 画像取得のSQL統合と画像データキャッシュを行う。
7. DB往復削減とviewer contextキャッシュを行う。
8. 検索、Memories、エクスポートを改善する。

各項目は別ブランチで実施し、ベンチ通過、スコア非悪化、整合性確認後にだけmainへ取り込む。

## 確認済み・未確認事項

### 確認済み

- 当日マニュアルの採点、FAIL、整合性、初期化、追試条件
- Go実装の主要APIとSQL
- PostgreSQLスキーマと既存インデックス
- 各リージョンから参照するDBホストの構成
- nginx、systemd、DBコネクション設定

### 未確認

- 初期ベンチのエンドポイント別負荷
- PostgreSQLの実データ件数とテーブルサイズ
- 各SQLの実行計画と実行時間
- CPU、メモリ、ネットワーク、ディスクI/Oの実測値
- ベンチマーカーの具体的なAPI遷移と並列度
