# ユーザー数の増え方の分析 (スコアが伸びない理由)

1位は約50万点、こちらは約5〜6万点。差の原因を、ポータルの Stdout、timeline/report.txt、DB (#10205 のデータ) から調べた。

## 結論

- **スコアは人数でほぼ決まり、人数は日ごとに「約2.5倍に増える」か「増えない (1倍)」かのどちらか**。8倍の差は、全リージョンで増え始める日が1〜2日早いだけで説明がつく
- サーバは遊んでいる (europe1 / america1 は idle 93〜97%、asia1 は約75%)。CPU の削減では差は縮まらない
- 人数は**日の初めにベンチマーカーが、前の日の結果を見て決めている**。登録の遅さが条件ではない
- 増えるかどうかは、そのリージョンの投稿期間作成 (admin の `POST /api/admin/posting-window`) の時間と強く相関する。ただし例外もあり、条件は特定できていない
- **asia の1日目→2日目は、どのランでも1倍**。europe / america は毎回1.7〜2.3倍。ここが最大のレバー

- 1日目は毎回 18 / 7 / 6 人。増える日は約2.3〜2.8倍
- #8691 の asia は、投稿〜友達フィードの完了率が100%なのに増えていない。完了率やフィードの速さは、増える条件ではなさそう
- 投稿期間は1リージョン9秒で、3秒ずつずらして開く (最後の期間だけ3リージョン同時)。6日 × 3リージョン = 18期間で固定

## 2. 時間内投稿は制約になっていない

- DB の `posting_windows` で、`on_time_deadline - starts_at` は全期間 **1日**。ベンチマーカーは `onTimeSeconds` を指定していない
- `lateSeconds` は常に0。過去のレポートにある「遅れ投稿で人数が伸びない」という推測は捨ててよい

## 3. admin の時間と翌日の倍率 (asia、2〜4日目→翌日)

| ラン | asia の admin (秒) | 翌日の倍率 |
|---|---|---|
| #8691 | 1.64 / 2.50 / 2.68 | 1.0 / 1.1 / 1.0 |
| #7477 | 1.13 / 1.10 / 2.46 | 1.5 / 2.4 / 1.7 |
| #8155 | 1.24 / 0.85 / 1.71 | 1.4 / 2.4 / 2.1 |
| #10205 | 0.58 / 0.46 / 0.55 | 2.6 / 2.8 / 2.5 |

- #10205 は `perf/notification-time-ordered-id` (通知IDを UUID v7 にしただけ、#42 で main にマージ済み)。asia の admin が速くなり、asia の人数が初めて伸びた
- europe / america の admin はほぼ常に 0.1秒未満で、毎回伸びている
- 例外: #8155 は asia の admin が 1.71秒でも2.1倍。#7477 の europe 5日目は admin 0.50秒でも 68→69 (投稿まで終えた人が 45 / 68 と少なかった)
- asia だけ admin が遅いのは、通知の行を `INSERT ... SELECT FROM users` で作っていて、asia の active ユーザーが 5175人いるため (europe 149人、america 77人。初期データを含む)

## 4. 登録のタイミング (#10205、DB の users.created_at)

| リージョン | 日 | その日の登録 | 最初の登録 (開始から) | 一度も投稿していない |
|---|---|---|---|---|
| asia | 3 | 32 | 0.45s | 3 |

| asia | 5 | 201 | **3.18s** | 8 |
| europe | 4 | 51 | 0.39s | 0 |
| america | 4 | 21 | 0.44s | 0 |

- 「N日目: X人」に書かれた人数は、その日の期間中に登録して、ほとんどがその日のうちに投稿している (例: asia 4日目は 47→131人の予定で、その日に88人が登録)
- asia 5日目は admin が 3.25秒かかり、最初の登録が開始から 3.18秒後まで待たされた。admin のリージョンのロック (`lockPostingWindowRegionExclusive`) が登録を止めている。人数は日の初めに決まっていても、その日に動ける時間が削られる

## 6. 打ち手の候補

1. **通知の行を作らない** (本命): admin は `posting_windows` に1行足すだけにし、SSE はそこから通知を組み立てる。admin が数十 ms になり、ロックで止まっていた登録・投稿も解放される。最後の期間が遅れて開く問題 (1件20点) も同時に直る
2. **グランプリの取りこぼし**: #10205 では asia 325人中 202人しか通過していない。最後の期間の同時投稿 (300〜500件) を捌けるようにする。画像を DB の外に出す案がこれに当たる
3. **europe1 / america1 に読み取りを持たせる**: 書き込みの応答の前に asia1 から各リージョンのメモリへ送り、届いたのを確かめてから返す。即時反映を保ったまま、読み取りの約100ms の往復 (ping 実測 100.8ms) をなくせる。規模が大きいので 1・2 の後
4. **人数の上限があるか**: アクセスログの接続元は506、各ランの5日目の合計は 411〜504。約500人が上限なら、やることは 1・2 に絞られる

次のベンチは 1 を単独のブランチで行い、Stdout で asia の2日目が18人から動くか、asia 1日目の admin が 0.1秒以下になるかを見る。
