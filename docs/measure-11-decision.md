# 施策11の判断材料: europe / america の処理を asia 側へ委譲するか

実行計画 (`docs/action-plan.md`) の施策11について、チームで採否を決めるための資料。
**規約上グレーな部分があり、違反と判断されれば失格になる**ため、実装前にチームで判断したい。

## 1. 決めたいこと

1. 施策11に取り組むか (取り組むなら、運営に確認してからか)
2. 取り組む場合の範囲: 全APIを転送するか、投稿・フィードなど一部に絞るか

## 2. 課題: europe / america のユーザーが期間内に活動を終えられていない

| 指標 | asia | europe | america | 出典 |
|---|---:|---:|---:|---|
| app → DB (asia2) の往復時間 | 約1ms | 約100ms | 約100ms | ベンチ #940 |
| `POST /api/posts` の平均 | 0.68秒 | 2.24秒 | 2.06秒 | PR #20 適用後 (`bench-results/021710`) |
| `GET /api/feeds` の平均 | 0.14秒 | 0.54秒 | 0.55秒 | 同上 |
| アプリの CPU 使用率 | 約70% (1コア換算) | 約3% | 約3% | 同上 |
| グランプリ (最終日) の検証を通過した人数 | 37人 | 1人 | 2人 | ベンチ #2540 (PR #20 適用前) |

- europe / america は**配点が1.5倍**なのに、最終日 (友達フィードの検証が20点) を通過できたのは各6〜7人中1〜2人だった (#2540)
- 欧米のアプリサーバは CPU がほぼ空いている。遅さの大半は **DB との往復待ち** (クエリ1本ごとに約100ms) と考えられる
- ベンチマーカーは、投稿の直後 (94.5%が1秒以内) に友達フィードを見て検証する (#2540 の行動分析)。投稿〜フィードを投稿期間 (約9秒) の中で終えられるかが、直接スコアになる
- 施策7 (PR #16、PR #20 で main に統合済み) でクエリの数は減らしたが、それでも欧米の投稿は約2秒かかっている
- PR #20 適用後のグランプリ通過人数は、まだ確認していない

## 3. 対応しようとしている内容

### 今の流れ

```
europe のユーザー → ルーター → europe1 (アプリ) ⇄ ルーター ⇄ asia2 (DB)
                                    └ SQL 1本ごとに約100ms。1リクエストで数回〜10回以上往復する
```

### 施策11の流れ

```
europe のユーザー → ルーター → europe1 (受け口) → ルーター → asia1 (アプリ) ⇄ asia2 (DB)
                                    └ europe1 ⇄ asia1 は1往復 (約100ms)。SQL は asia1 から約1ms で実行
```

- 公開の入口 (europe1 / america1) とユーザーの地域判定は今のまま残す
- europe1 は、受けたリクエストを asia1 の**内部用の口**へ転送し、結果をそのまま返す
- 見込み: 投稿は「SQLの往復回数 × 100ms」が「約100ms + 画像の転送」に縮む。速度が何倍になるかは未計測

### やり方の候補

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **全面転送** | europe1 / america1 の nginx で `/api/` を全部 asia1 に転送する | 実装が小さい (nginx の設定と asia1 側の受け口だけ) | 欧米のアプリは実質使われなくなる。規約上いちばんグレー。asia1 に負荷が集中する |
| **一部だけ委譲** | 投稿とフィードなど、往復が多く得点に直結する API だけを asia1 で処理する (Dots の分析 B4) | 効果の大きい所に絞れる。規約上の説明もしやすい | 実装が大きい (API ごとに転送の口を作る) |

### どちらの案でも必要になる変更

- **地域チェックの扱い**: 今のアプリは、europe のユーザーが asia1 に来ると `region_mismatch` (403) で拒否する (`go/region.go`)。内部用の口だけは「入口は europe」として扱い、このチェックを入口の地域で行う
- **内部用の口の保護**: 一般のクライアントやベンチマーカーが「入口は europe」と偽れないようにする (秘密のヘッダーで認証し、外部からのリクエストではヘッダーを捨てる)
- **元のクライアント IP**: `X-Client-IP` をそのまま引き継ぐ (IP BAN とログの判定に使われている)
- **転送の宛先**: europe1 / america1 から asia1 へ届く内部アドレスを、環境変数 (`etc/env/*.sh`) で設定する
- **再送をしない**: 転送に失敗したときに自動で再送すると、投稿やコメントが二重に登録されるおそれがある

## 4. 迷っているポイント

### 4-1. 規約に違反しないか (最大の論点)

当日マニュアルの該当箇所:

> 公開済みレギュレーションの範囲で、サーバ内のソフトウェア、DBスキーマ、インデックス、保存方式、アプリケーションの実装を変更できます。
> 固定リージョン、公開先、ルーター経由の通信を維持してください。
> (docs/manual.md:235, 239)

> 主催者の指示以外で利用が認められたサーバ以外の外部リソースを使用する行為（他のサーバに処理を委譲するなど）
> ルーターを迂回するサーバ間通信や、ベンチマーカーとの通信
> サーバのリージョン、通信遅延、帯域制限を変更または回避すること
> (docs/manual.md:658, 674-675 の禁止事項)

| マニュアルの記述 | 施策11 | 判断 |
|---|---|---|
| 認められたサーバ以外に処理を委譲しない | 委譲先は自チームの asia1 (認められたサーバ) | 問題ない |
| ルーターを迂回しない | europe1 → asia1 がルーターを通る経路なら問題ない | **未確認** (4-2 参照) |
| サーバのリージョンを変更しない | europe1 の設定 (`ISUREAL_REGION=europe`) は変えない | 問題ない |
| **固定リージョンを維持する** | europe のユーザーの処理を、実質的に asia1 が行う。アプリの「europe のユーザーは europe1 で処理する」チェックを、内部用の口で入口の地域に置き換える | **グレー** |
| **通信遅延を回避しない** | 遅延そのものは消えない (europe1 ⇄ asia1 で1往復かかる)。何度も遅延を払う構成を1回にする | **グレー** |

**問題ないと考える根拠**
- 施策7 (SQLをまとめて往復を減らす) と同じく、「遅延をはさむ回数を減らす」実装の工夫である。遅延や帯域の設定そのものには触れていない
- 委譲先は認められたサーバで、通信はルーターを通る
- 入口の地域とユーザーの地域判定は維持している

**違反と判断されうる根拠**
- 「固定リージョン」は、各地域のユーザーをその地域のサーバで処理するという問題の前提とも読める。全面転送では欧米のアプリがほぼ素通しの中継になり、この前提を崩している
- 「通信遅延の回避」を、「地域間の遅延が効かないように構成を変えること」と広く読まれると該当する
- 違反の場合は失格で、それまでのスコアがすべて無効になる。期待できるスコアの上積みに対して、損失が大きすぎる

### 4-2. 技術的に成り立つか

| 論点 | 内容 | 状態 |
|---|---|---|
| 転送経路 | europe1 から asia1 に HTTP で届く内部アドレスがあるか。その通信がルーターを通るか (遅延がかかるか) | 未確認。env では asia2 (DB) は `192.168.4.10`。asia1 のアドレスは不明 |
| asia1 の CPU | PR #20 適用後でアプリが約70% (1コア換算、2コア中)。欧米の処理が加わると足りなくなる可能性がある | 未計測 |
| 画像の帯域 | 投稿の画像は、転送しても一度は地域間を渡る。帯域の制約は消えない | 変わらない |
| SSE 通知 | PR #14 でサーバごとに通知を配る仕組みになった。転送すると欧米の接続を asia1 が持つことになる。SSE は転送の対象から外すのが無難 | 要設計 |
| IP BAN とログ | asia1 で動く `isureal-guard` がログを読んで BAN している可能性がある (施策14)。転送すると、欧米のリクエストのログが asia1 に出る / 二重に出る | 施策14の調査待ち |
| 内部の口の悪用 | 秘密のヘッダーが漏れたり、外部から付けられたりすると、地域チェックを回避できてしまう | 要設計 |
| 初期化 | `/api/initialize` は asia1 で処理されるので影響しない | 問題なし |
| 追試 (再起動) | 転送先の設定が再起動後も有効か | 要確認 |

### 4-3. 効果の見込み

- PR #20 適用後でも、欧米の投稿は約2秒、フィードは約0.5秒。往復1回が約100ms なので、投稿ではまだ十数回分の待ちが残っている計算になる (画像の転送時間を含む)
- 委譲すれば、投稿は「1往復 + 画像の転送 + asia1 での処理」になる。グランプリ通過人数がどこまで増えるかは試すまで分からない
- 施策7のさらなる削減 (セッション確認、投稿のトランザクションなど) でも、ある程度は縮められる。ただし往復を1回まで減らすのは難しい

## 5. 選択肢と推奨

| 選択肢 | 内容 | リスク | 手間 |
|---|---|---|---|
| A. 見送る | 施策7の残り (セッション確認・投稿のトランザクション) と施策8 (画像のキャッシュ) で欧米を詰める | なし | 中 |
| **B. 運営に確認してから決める (推奨)** | ポータルから質問する。回答を待つ間は、A を進めつつ転送経路の確認 (4-2) だけ行う | なし | 小 (確認のみ) |
| C. 一部だけ委譲する | 投稿とフィードだけを asia1 で処理する。運営の回答で問題ないと分かってから着手 | 回答次第 | 大 |
| D. 全面転送する | nginx で `/api/` を asia1 へ転送する | **失格のおそれ** | 小 |

**推奨は B。** 運営が問題ないと回答したら C から着手し、効果を見て範囲を広げる。回答がない、またはグレーのままなら A に専念する。

### 運営への質問の文案

> europe1 / america1 が受けた API リクエストについて、アプリケーションの処理としてルーター経由で asia1 に転送し、asia1 で DB の処理を行った結果を europe1 / america1 から返す構成を検討しています。入口のサーバと、ユーザーの地域の判定は変えません。この構成は、当日マニュアルの「固定リージョンの維持」および「通信遅延の回避の禁止」に抵触しますか。

## 6. 判断の前に確認できること (サーバ上で読むだけ)

```bash
# europe1 から asia1 への経路と遅延 (asia1 の内部アドレスは ip addr で確認)
ssh asia1 ip -4 addr
ssh europe1 ping -c 5 <asia1の内部アドレス>
ssh europe1 traceroute <asia1の内部アドレス>
```

- ping が約100ms なら、ルーターの遅延がかかっている (ルーターを通っている) と考えられる
- 1ms 程度で届く場合は、ルーターを迂回する経路の可能性があるので**使ってはいけない**
